# ADR 0003 — 只收 CSV，不做 XLSX 解析

- **状态**：已接受（Accepted）
- **日期**：2026-11-19
- **取代**：[ADR 0001](0001-xlsx-support.md)（XLSX 支持策略）
- **决策**：`loan_audit` 只接受 `.csv` / `.tsv` 文本；遇到 `.xlsx` 明确报错并指引先转换。插件保持**零运行时依赖**。

---

## 1. 背景

ADR 0001 决定引入 `fflate`（仅解压）+ 自写解析层来处理 `.xlsx`，理由是「要求用户另存为 CSV 是真实流失门槛」。

实际排期到阶段 C 时重新评估，结论变了：**这一层复杂度和它带来的价值不成比例，而且它有更便宜的替代路径。**

## 2. 为什么改主意

| 原来的顾虑 | 重新评估 |
|---|---|
| 用户不会「另存为 CSV」 | 模型可以替他做：DSH 已装 office/Univer 能力，能把 xlsx 读成表格文本再交给插件。用户只需拖文件，不需要懂格式 |
| 依赖第三方插件，可用性不由我们决定 | 只在「用户拿的是 xlsx」这条路径上需要它；CSV/粘贴文本路径零依赖。而且失败时报错可行动，不是死路 |
| 自写解析 ~400 行，要处理合并单元格、1904 基准、无缓存公式 | 这是**永久维护负担**：每家银行导出的表都不一样，bug 会持续来。而它只解决「打开文件」这一件事，不产生任何业务价值 |
| 零依赖是卖点 | 保持零依赖本身就是卖点，且省掉一条供应链风险 |

一句话：**解析 xlsx 不是这个插件的价值，核对数字才是。** 把不产生价值的部分外包给宿主已有的能力，是更诚实的分工。

## 3. 决策

1. `loan_audit` 接受两种输入：
   - `path`：`.csv` / `.tsv` 文件路径
   - `csvText`：直接粘贴的表格文本（模型转换后的结果也走这条）
2. 传入 `.xlsx` / `.xls` 时**明确报错**，并给出可执行指引：
   > 不支持 Excel 文件。请用表格能力把它转成 CSV 文本后通过 `csvText` 传入，或让用户另存为 CSV。
3. 工具 `description` 里写清这一点，让模型**在调用前**就规划好转换，而不是撞了墙再改。
4. 编码：UTF-8 / GBK / GB18030 自动探测（Node 内置 `TextDecoder`，无依赖）。ADR 0001 的这条承诺**保留**。
5. 表头探测、列映射契约、`status: "needs_mapping"` 回吐网格——ADR 0001 设计的这套交互**全部保留**，只是输入从「二进制文件」变成「文本」。

## 4. 代价

- **用户多一步**：xlsx 用户需要模型先转换。转换失败时体验会断在那里。
- **数值可能经过模型**：如果模型不是用工具机械转换，而是自己抄表格，就会引入转写错误。这原本是 ADR 0001 明确要避免的。
- 极端格式（多重表头、合并单元格）在转换环节就可能丢失结构。

## 5. 转写风险怎么兜

既然数字可能经过模型，就必须让**错的数字失败，而不是安静地算出一份错的报告**：

1. **不变量校验（硬性）**：本金分项合计必须等于合同本金；末期余额必须为 0。任一不成立 → 拒绝出结论，返回差异明细。
2. **来源标注**：`data.source.kind` 区分 `csv-file` / `csv-text`；`csvText` 路径的报告里出现「数据由文本传入，请对照原表核对」。
3. **抽样回显**：报告里回显前 3 行原始单元格值，用户能一眼看出有没有串列。
4. **不做静默修补**：某期金额解析失败就记 `warnings` 并标注「部分未解析」，绝不丢弃该行后给一个干净总额。

## 7. 什么情况下应该推翻

1. 真实使用数据显示：超过 **30%** 的尝试以「用户给的是 xlsx、转换又失败」告终 → 回到 ADR 0001 的方案，引入 `fflate`。
2. 出现大量「数字抄错」投诉，且都能追溯到模型转写 → 说明转换必须机械化，此时要么解析 xlsx，要么要求用户手动另存为。
3. DSH 提供官方的「文件 → 表格文本」工具能力 → 直接把指引指向它，不自己实现。
